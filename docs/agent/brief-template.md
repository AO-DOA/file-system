# 派单任务书模板（七段式）

**怎么用**：复制 §0 的骨架 → 替换所有 `{{占位符}}` → 其余**逐字不要改**。七段里只有
「§3 本段范围」「§7 里的授权改动面」是本段变量，外加背景里的段号/基线/规格三个填项；
其它六段是固定条款，写死是为了让子代理每次都拿到同一套安全边界与同一套验收口径。

改模板本身要谨慎：§7 是安全边界，其余六段是**历次派单里被验证过有效的写法**。要改先看
`docs/agent/lessons.md` 里有没有相关的负结果。

---

## 0. 骨架（可整段复制）

```markdown
# 任务：{{一段话目标}}（{{本段属于元工作 / 产品工作}}，不碰 {{不该碰的东西}}）

## 1. 背景
- 工作区（唯一可写）：`{{仓库路径}}`
- 基线：`{{基线提交}}`（**开始前先 `git status --porcelain` 确认为空**）
- 依据：`{{规格文件}}`（需求与裁决的唯一依据；与之冲突的一切转述都不作数）
- 本段是第 {{段号}} 段：{{前一段做了什么、本段接着做什么}}
- **入场必读顺序**见 `docs/agent/README.md` §3；已验证的负结果见 `docs/agent/lessons.md`——动手前先看有没有正好压在本段方案上的「别再试」。

## 2. 最高原则
1. **只做本段的事**。范围外的改进一律不做，发现了写进报告，不顺手改。
2. **先把前提核一遍**。本任务书是人写的、会错（数字、路径、结论都可能错）。开工第一步是复现书里的每个事实性断言，错了就在报告开头写「你给的前提里，哪几处需要订正」，然后按订正后的做。
3. **不改别人有意保留的行为**。`PROGRESS.md` §3 标为「有意差异 / 有意保留」的，不是 bug。
4. **数字必须来自可复跑的产物文件**。转述、估算、推断都要显式标出来源与性质。
5. **拿不准就停下来问**，不要用试错代替判断：宁可写清「我需要改 X，因为 Y，请裁决」。

## 3. 本段范围（变量）
{{本段范围：要建/要改什么，逐项列，含验收标准}}

## 4. 硬约束
- **不许改**：{{禁改清单}}。本段只做 {{新增 / 修改}} —— 不做 {{其它}}。
- **允许新增**：{{允许新增清单}}。
- **唯一允许的既有文件改动**：{{若有，写清哪一行；没有就写「无」}}。改的时候严格照该文件既有的格式风格，不要重排其他内容。
- 不许 `git add` / `commit` / `checkout` / `reset`（提交由主代理做）；不许跑 `npm run build`；不许重启 `dsh web`；不许改 DSH 本体（`{{DSH 检出路径}}`）。
- 中文注释与文案，风格与仓库既有文档一致（讲因果、不讲废话）。

## 5. 验证方式
逐条列出主代理**会亲自复跑**的命令，子代理必须自己先跑一遍并把原始输出贴进报告：
1. {{本段专属的验收命令，如 `node scripts/verify-stage.mjs --allow …`}}
2. `npm run typecheck`（期望 exit 0、无输出）
3. `npm run lint`（期望 0 错 0 警告）
4. `npm test`（期望 {{预期 spec / 例数}}；写清这个数是从哪来的）
5. `git status --porcelain`（确认只有 {{预期改动面}}）
**范围守卫**：凡改动落在授权面之外的，报告里必须显式标红——越界的绿不是绿。

## 6. 报告要求
- 详细报告写 `{{报告路径}}`（**仓库内**，不要写 `/tmp`——`/tmp` 不是共享层）；最终回复 ≤{{N}} 行摘要。
- 报告必须包含：{{逐项要求，至少含：每个产物的一句话用途 / 关键命令的实跑输出 / 证据文件路径}}。
- **诚实列出未核实项**（单独一节）：哪些是实测、哪些是推断、哪些没跑。
- **待裁决项单独一节**：本段自己拍的板、改了上游已落地数值的地方，都要拎出来。

## 7. 授权与否决
- 授权：{{读任何文件 / 跑上述命令 / 写 {{可写路径}} / 新增 {{可新增清单}} / 改 {{唯一允许的既有文件行}}}}。
- 否决：{{否决清单：改产品代码 / 改测试 / 改既有文档正文 / git 写操作 / build / 重启服务}}。
- 需要越权时停下来写清「我需要改 X，因为 Y，请裁决」。
```

## 1. 各段的固定理由（给写任务书的人看）

| 段 | 变量还是固定 | 为什么这么定 |
|---|---|---|
| §1 背景 | 骨架固定，填段号/基线/规格 | 基线提交与规格路径是子代理**无法自行推断**的两件事；入场必读与 lessons 的指针写在这里，保证每个子代理都被指向同一份共享层 |
| §2 最高原则 | **固定** | 五条都是从历次返工里长出来的：「前提会错」对应实测里三份报告开头的「你给的前提里，N 处要订正」；「数字来自产物」对应转述失真；「有意保留不是 bug」对应 G 系列行为差异 |
| §3 本段范围 | **变量** | 唯一真正每段不同的东西。写清验收标准，别只写动作 |
| §4 硬约束 | 骨架固定，填清单 | 禁改清单与授权面必须成对出现——只有授权没有禁止，子代理会顺手把「显然该改的」也改掉 |
| §5 验证方式 | **固定** | 验收命令必须每次一样，否则「全绿」不可比。期望值要写清出处，否则数字会随记忆漂移 |
| §6 报告要求 | **固定** | 「写进仓库不写 `/tmp`」「未核实项单独列」「待裁决单独列」三条是经验卡与验收能成立的前提 |
| §7 授权与否决 | **保留全文** | 这是安全边界，不因段而变；越权出口（「停下来写清需要改什么」）必须在任务书里给出，否则子代理只能自行判断 |

## 2. 反面写法（别这么派）

- ❌ 「优化一下顶栏」——没有验收标准，子代理只能自己发明一个，然后自己宣布通过。
- ❌ 「参考上次的报告」——上次报告在哪？没有路径的引用等于没说。
- ❌ 「顺便把 X 也修了」——范围一松，范围守卫就失效。
- ❌ 只给「改哪几个文件」，不给「不许改哪几个」——`PROGRESS.md` §3 里那些有意保留的行为会被当成 bug。
- ❌ 让子代理「看着办」——子代理看不到主代理的会话上下文，它的「看着办」是另一套假设。
