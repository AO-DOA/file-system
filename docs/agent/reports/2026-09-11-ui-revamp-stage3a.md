## 3. 阈值标定（470px 怎么来的）

容器是 `.fs-hbar` 自身（`container-type:inline-size`），**hbar 宽 = 面板宽 − `.fs-wrap` 左右内边距 28px**。

1. **上一档的切换点（复现）**：面板 700 ⇒ 三个按钮的 label `offsetWidth === 0`（图标态）；面板 710 ⇒ 可见。即 hbar 672 ± 1。
2. **本档要解决什么**：三按钮图标化后，右列仍会被挤出容器。实测最坏场景（S2 = 长工作区名 + 长路径 + 四字视图名）在工作区名可见时，**面板 460 起右列才全部可达**（459 及以下有整块裁掉）。
3. **无缝下限**：工作区名可见区间是 `hbar > N`。要它整段安全，必须 `N ≥ 460 − 28 = 432`。
4. **留缝反证（实测）**：取 `N = 428` ⇒ 面板 **457 / 458 / 459** 三档工作区名可见且右列被整块裁 1 个（`out-n428.json`）。这就是你提到的缝。
5. **余量**：沿用上一档同一口径（绝对像素端点会随字体渲染小幅移动），按约 8% 取整：`432 × 1.08 ≈ 466` ⇒ 取 **470**（面板 498）。
6. **落地后实测切换点**：面板 **498** 工作区名 `offsetWidth === 0`（工作区按钮由 202.8px 收到 **44px**）；面板 **499** 恢复可见。与 `470 + 28` 一致。

**阈值敏感度**（B 方案，见 §6）：N 再放大只影响「工作区名可见区间」与 499–534 那段的**部分裁切**（视觉级），对门禁四项指标无影响：

| N（hbar） | 工作区名让位 | 右列整块裁下界 | 右列整块裁档数 | 右列部分裁切档数 |
|---|---|---|---|---|
| 470（落地） | ≤498 | 314 | 412 | 600 |
| 490 | ≤518 | 314 | 412 | 542 |
| 510 | ≤538 | 314 | 412 | 526 |

（要让 499–534 那段「部分裁切」也彻底消失，需要 N ≥ 550；带来的代价是工作区名可见区间再缩 80px。**我没有这么做**，见 §7 待裁决 1。）

3. B 把同列重叠**全档归零**（504 → 0），代价是下界从 284 退到 314：314 仍在门禁的 360 以内，而且这 30px 的面板**在基线上本来也是整块裁掉的**（基线右列下界 441/459）⇒ B 没有让任何一档「从可达变成不可达」，A 只是额外把 284–313 救回来而已。
4. B 的代价里**唯一算得上新引入的**是面板 499–534 的「部分裁切」（保存按钮右边缘少 17px、仍可点，`out-final.json` + dump 面板 500：保存 raw `[459.5,503.5]` / vis `[459.5,486]`）：基线同区间干净，B 因为 genwrap 保住了 min-content 而更早溢出。门禁口径（整块裁掉）不覆盖它，我在这里显式登记。

## 7. 未核实项（诚实清单）

1. **没有真实 GUI 端到端**：全部几何结论来自 headless Chrome（`/usr/bin/google-chrome` 153.0.8010.36）探针；按指令未跑 `npm run build`、未重启 `dsh web` ⇒ 运行中的 `client/client.js` **仍是旧版**，页面上还看不到本段改动。没有任何人真的在浏览器里拖过面板宽度。
2. **探针图标是 16×16 占位 `<rect>` svg**（沿用第一、二段同款），未复刻真实图标 path；`Button` 的 `.icon` 容器是固定 16×16，不参与宽度计算，故几何结论不受影响 —— 但这是我**沿用的判断**，本轮没有单独验证。
3. **绝对像素端点会随字体可用性移动**（本机 Linux Chrome）。470 是按 8% 余量标的；换字体族需复测切换点 498/499。
4. **探针场景是构造的 7 个**（3 档工作区名 + 3 档路径 + 6 种按钮组合），不是真实工作区全量样本。
5. **「右列部分裁切」是本段自加的第五指标**，你给的门禁只有四列；它的判据（可见宽 < 原始宽 − 0.5px）**没有与上一段的既有指标做过口径对齐**，只能横向比较（基线 577 档 / A 449 档 / B 600 档）。
6. **「可点」只做了中心点 hit-test**：探针不模拟真实指针事件；499–534 那段「保存按钮被切掉右边 17px」在真实浏览器里能否点到、误点概率多大，未验证。
7. **没有验证容器查询在真实宿主里的行为差异**：探针把 `.fs-hbar` 放进 `.fs-wrap` 量宽度，与 GUI 里 DSH 侧栏/主区分屏布局下的实际容器宽度可能不同（宿主注入 `--dsh-composer-height` 等变量，探针只取了壳层 CSS）。
8. **`aria-label` / `title` 的可访问性**只在 jsdom 里断言了属性值，没有跑真实屏读器或 axe。
9. **`docs/spec-ui-revamp.md` §7 与 `PROGRESS.md` §5 #8/#9 的台账没有更新**：这两个文件不在本次授权的三个文件里，我没有动（见 §8 待裁决 4）。
