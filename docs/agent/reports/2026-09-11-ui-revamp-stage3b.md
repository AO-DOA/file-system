### 3.2 语义（上游裁决，照此实现 —— 这里明确写出来）

**右侧副本 = 视图类型冻结、内容数据实时、强制只读。不是历史快照。**

| 维度 | 实现方式 | 证据 |
|---|---|---|
| 视图类型**冻结** | 开启那一刻把 `viewer.mode` 存进 `SplitState.mode`；右侧 viewer 用 `{...viewer, mode: splitState.mode}` —— 左侧之后 `setMode` 只改左边 | 单测 `freezes the right pane view while the left keeps switching`：左侧切到「源码注解」后，右侧仍是源码正文（`# Full`），左侧是注解文档（`# Title`） |
| 内容数据**实时** | 右侧 viewer 与左侧是**同一个对象的浅拷贝**，`source`/`docData`/`annotData`/`trData`/`fold` 字段共享，没有第二份数据副本、没有发起第二次 `/read` | 代码层面（`{...viewer}`）；「左侧保存后右侧跟着刷新」的端到端链路**未验证**（需 build + 重启 + GUI，见 §7） |
| **强制只读** | `editMode` 恒 false ⇒ `FsPane` 天然只走查看分支（它的 `else if (v.editMode)` 分支进不去）；顶栏只有一份，右侧窗格里**没有任何按钮** | 单测：左侧进编辑态时 `.fs-area` 只有 1 个且在左侧；右侧窗格内 `button` 计数为 0 |
| 开关 | **同一个按钮再点一次即关闭** | 单测 `copies the open view to the right, and the second click closes it` |
| 按文件记忆 | `Record<opened.path, SplitState>`；关闭只置 `on:false`（比例与冻结视图留着） | 单测 `remembers the split per file…` 与 `drags the divider…remembers it per file` |
| 拖拽分栏 | 复用左侧树宽的 `.fs-split` + document 级 `mousemove`/`mouseup`（按 G-7 既有行为不做卸载清理）；记的是**占比**，clamp [0.2, 0.8]；`flexGrow = p/(1−p)` 落到样式 | 单测：初始 grow=1（占比 0.5）、拖到底分别夹到 0.25 / 4；探针在面板 800 量到左右窗格各 **240.5px**（占比 0.5 的分配成立） |

**一处实现细节（我在写测试时发现并改正的）**：占比的分母必须是「两侧弹性宽之和」（拖拽期间不变），不能写成 `新右宽 + 左宽` —— 后者会随拖拽漂移（我第一次写成那样，单测直接抓出来了：把 0.9 夹到 0.8 的路径算成了 0.643）。

### 3.4 分屏按钮的位置与收纳（实测裁决）

**放右列**（`{splitBtn}{genWrap}{editActions}`，最前）。代价实测：

| 指标 | 第三段 a 末态（无分屏按钮） | 本段末态（含分屏按钮） | 门禁 |
|---|---|---|---|
| 右列被整块裁的下界（最坏场景，面板） | 314 | **356** | ≤360 ✅（**余量 4px**） |
| 跨列重叠 / 同列重叠 | 0 / 0 | **0 / 0** | 0 ✅ |
| 顶栏高度集合 | {48} | **{48}** | 单行 ✅ |

**但只加分屏按钮、不动首档阈值会新开一个窗口**（逐档实测，步长 1）：

| 阈值 | S1 中列被裁 | S2 中列被裁 | S6 中列被裁 | 右列部分裁切 |
|---|---|---|---|---|
| 672（不动） | 200–**703** | 200–**720** | 200–**720** | 到 720 |
| **760（本段落地）** | 200–400 | 200–400 | 200–400 | 到 400 |

成因：面板 701–720 时 hbar 已越过 672 的图标化档，右列四个按钮的文字**同时回来**，把中列挤到 0（视图名被裁）并让右列轻微溢出。**逐档 diff 确认 760 相对 672 没有任何一档变差**（变差 0 档，只有 S1 的 701–703、S2/S6 的 701–720 变好）。
760 的标定：窗口上界是面板 720 ⇒ 阈值不得低于 hbar 692（= 720 − 28）；按与上一档同样的约 8% 字体余量取整为 **760**（实测切换点：面板 788 仍是图标态、789 恢复文字）。

**我没有把它挪到左列**：左列同样是 `auto` 列，min-content 一样计入三列之和；挪过去不会改善 701–720 的窗口，只会把「工作区名」挤得更早让位。**「纳入同一套收纳」（把首档阈值一起抬高）才是对症的做法**。

### 3.5 分屏开启态对顶栏几何的影响

同一探针加 `--splitpane`（右侧多一条分隔条 + 一份窗格）再跑 3857 档：四项指标与未分屏态**逐档完全相同**（跨列 0 / 同列 0 / 右列整块裁 754 档 [200–356] / 顶栏高 {48}）。分屏窗格只进 `.fs-body`，顶栏 DOM 不随开关变化。

## 7. 未核实项（诚实清单）

1. **没有真实 GUI 端到端**：全部几何结论来自 headless Chrome（`/usr/bin/google-chrome`）探针；按授权未跑 `npm run build`、未重启 `dsh web` ⇒ 运行中的 `client/client.js` **仍是旧产物**，页面上看不到本段（也看不到前三段）的任何改动，没有任何人真的在浏览器里点过分屏按钮或拖过分栏。
2. **「左侧保存后右侧内容刷新」没有端到端验证**：这条只有代码层面的依据（右侧 viewer 与左侧共享同一批数据字段、不发起第二次 `/read`），没有在真实 GUI 里保存过文件看右侧是否跟着变。
3. **分栏拖拽只在 jsdom 里验证了比例换算**（clamp + 记忆 + `flexGrow` 值）；真实浏览器里的手感、以及除 0.5 之外的占比实际分出的像素宽度**没有量过**（探针只量了占比 0.5 的一档：左右各 240.5px）。
4. **分屏状态没有落盘**：需求原文是「按文件各自记忆」，我实现为**同一会话内按 `path` 索引**（`FsView` 的组件 state），**不跨界面刷新持久化**（`localStorage` 的 `fs.ui.v1` 里没有 split 字段）。若你要的是「刷新后仍记得」，需要另加字段——请裁决。
5. **探针的 S0 场景与真实顶栏不一致**：真实「无打开对象」时右列仍有「解读选择」按钮（它无条件渲染），而探针的 S0 场景没有它 ⇒ S0 的右列比真实窄。门禁的最坏场景不在 S0（S1/S2/S4/S6 都含 gen 按钮），故**未影响门禁结论**；但 S0 那 10 档「右列部分裁切」在真实页面上会更严重一些，未单独测。
