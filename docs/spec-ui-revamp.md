## 1. 需求

### R1 — 顶栏生成入口收编为「解读选择」

**现状**：`genItems` 只有三态 —— 目录节点恒 1 项（folder）、md 文件恒 `[]`（因为 md 不生成 L2/L3）、其它文件恒 `file` + `src`；「翻译」是独立按钮（`trBtn`）。

**目标**

| 项 | 行为 |
|---|---|
| 按钮文案 | 「生成解读」→「解读选择」 |
| 菜单项 | **按当前文件类型自动适配**，不给无关功能留位置 |
| 目录节点 | 目录概览 |
| 文件节点 | 文件摘要、源码注解 |
| 项目内非 `.book/` 的 md | **仅翻译** —— md 不生成 L2/L3，host 侧对 md 直接拒绝（`errGenMd`），故不列文件摘要/源码注解 |
| `.book/` 内的 md | 无生成入口（书库文档不是翻译对象） |
| 独立翻译按钮 | 取消（并入本菜单） |

**判据**：对目录 / 普通文件 / 项目内 md / 书库内 md 四类分别断言菜单项集合。

### R3 — 视图标签合并为「视图选择器」

**现状**：`viewer.modes` 按 `doc → annot → tr → source` 推入数组，渲染成一排胶囊（Pill）。

**目标**

| 项 | 行为 |
|---|---|
| 形态 | 单个按钮 + 悬停下拉，取代一排胶囊 |
| 默认 | 按钮文字「源码」，**同时默认展示源码界面** |
| 按钮文字 | **必须等于当前显示的视图名，不得分离**（用户明确要求） |
| 点击按钮 | 选中按钮所示视图（幂等；点什么就是选择看什么） |
| 悬停按钮 | 弹出下拉，列出**其余已具备**的视图 |
| 未生成的不列 | 不具备的视图（如未生成的摘要 / 未翻译的译文）不进下拉 |
| 顺序 | 源码 → 文件摘要 → 源码注解 → 文章翻译 |

**默认视图改为源码优先**：现状是 `hasDoc ? 'doc' : (hasSource ? 'source' : (hasDocSrc ? 'annot' : 'source'))`（有摘要就先显示摘要），本规格改为源码优先。

**判据**：`hasDoc` / `hasDocSrc` / `hasDocTr` / `hasSource` 的组合下，下拉项集合与按钮文字。

### R5 — 视图选择器搬到右侧、与「解读选择」同组（2026-09-13 用户裁决）

**现状**：视图选择器（R3 的产物）挂在顶栏**中列** `.fs-hbar-mid`（中列 = 视图选择器 + 路径），
右列是分栏 / 解读选择 / 未保存 / 编辑⇄保存。

**目标**

| 项 | 行为 |
|---|---|
| 位置 | 视图选择器由 `.fs-hbar-mid` 移到 `.fs-hbar-right`；中列自此**只剩路径**，不再持有任何按钮 |
| 右列次序 | 视图选择 → 解读选择 → 编辑⇄保存 → 分栏 |
| 交互语义 | **一字不改**：点击按钮主体 = `viewer.setMode(viewer.mode)`（同值 bail out、真 no-op）／外层 `.fs-viewwrap` 的 `onMouseEnter` 开下拉／`Menu` 传 `portal`／`closeOnPointerLeave`／刻意不挂 `Tooltip` |
| 元素 | **不新增任何 DOM 元素、不新增图标**：只改 JSX 顺序 + 随之失效的 CSS 与注释 |

**判据**：`.fs-hbar-mid` 内按钮数为 **0**；`.fs-hbar-right` 直接子项次序为
`视图选择 → 解读选择 → 编辑⇄保存 → 分栏`；视图选择器仍无 `.fs-btnlabel` 层、仍不挂气泡
（`tooltipLabel(viewBtn()) === null`）。

**代价（已实测、已裁决、已修）**：右列 min-content 多出一个约 68px 宽的胶囊 + 一处 6px gap ⇒ 纯搬
位置时右列「被整块裁」的下界由 **307 抬到 389**（面板；最坏场景 S2/S6），**破门禁 ≤360**。四条收纳
候选逐条实测后用户裁决 **候选 B（窄档把「分栏」整块收起）**，落地见下面的 **R5.1**：下界回到 **339**
（余量 21px），跨列 / 同列可见重叠仍 **0 档**、顶栏高恒 **{48}**。逐档 diff、单档取证与代价见
`docs/agent/reports/2026-09-13-view-picker-to-right.md`。

### R5.1 — 窄档收纳：分栏按钮整块让位（2026-09-13 用户裁决「候选 B」）

**要解决的问题**：R5 的搬入让右列 min-content 抬高约 74px ⇒ 纯搬位置态右列「被整块裁」的下界
**389**（门禁 ≤360，破线 29px）。中列已可被压到 0、左列已收到最小，右列每一项又都是功能键或状态
标记 ⇒ 只能减少**右列** min-content。

**做法**（只加一条容器查询规则 + 一个既有按钮上的类名，**不新增任何 DOM 元素**）：

| 项 | 值 |
|---|---|
| 规则 | `@container (max-width:620px){.fs-hbar-right > .fs-tipwrap:has(.fs-splitbtn){display:none}}` |
| 锚点 | 分栏按钮上的类名 `fs-splitbtn`（加在既有 `<Button>` 上）。样式表用 `:has()` 从它找到外层的 `.fs-tipwrap` **一起**藏 —— 只藏内层 `button` 会留下一个 0 宽却仍占一处 6px gap 的锚点层 |
| 阈值 620 | 端点＝分栏按钮**不再被裁**的容器宽 **573px**（面板 601 − `.fs-wrap` 左右内边距 28px；面板 ≤600 时它正是右列唯一被裁的那一项，`partRightN` 恒为 1），按本仓「约 8% 字体余量取整」的惯例 573 × 1.08 ≈ 619 ⇒ **620** |
| 生效边界（实测） | 面板 **≤648 收起、649 起显示**（`--dumpW=648` 的 `fs-splitbtn` raw 宽 **0**；`--dumpW=649` raw 宽 **36.0** 且与 vis 等宽 —— 显示时完整不被裁） |
| 兼容性 / 降级 | `:has()` 是**渐进增强**：不支持它的浏览器（Chrome < 105 / Safari < 15.4 / Firefox < 121）**丢弃整条规则、静默失效** ⇒ 分栏按钮不隐藏 ⇒ 右列整块裁下界**回到 389（破门禁 ≤360）**。**是优雅降级，不是功能损坏**：所有功能键都在，分栏按钮可见可点，开/关分屏的入口比支持的浏览器还多；只有这条门禁指标本身失守。**代价**：这条规则的验收结论只在支持 `:has()` 的浏览器上成立，换浏览器复测时须先确认这一点 |

**为什么不并进既有的 760 档**：两条规则读数**逐档完全相同**（3857 档 × 全部字段 **0 差异**），差别只在
「分栏入口消失」的面板区间 —— 并进 760 会把它从 ≤648 扩到 ≤788，窄档收纳没有理由多牺牲 140 档宽度。

**验收（`--wsicon`，7 场景 × 551 档 = 3857 档）**：右列被整块裁下界 **389 → 339**（✓ ≤360，余量 21px）；
跨列可见重叠 **0 档**、同列可见重叠 **0 档**、顶栏高恒 **{48}**；被裁合计 916 → **624 档**、右列部分裁切
1045 → **777 档**；相对搬位置态逐档 diff **变差 0 档 / 变好 1184 档**；分屏开启态（`--splitpane`）与默认态
**逐档逐字段 0 差异**；既有两档的切换点不受影响（`wsLabShown` 578/579、`genLabShown` 780/790）。产物
`out-final-lian3.json` / `out-final-lian3-split.json`。

**代价（已实测，属「已知边界，不修」）**：容器 ≤620（面板 ≤648）时**开/关分屏的入口随按钮一起消失** ——
`toggleSplit` 在源码里的**唯一调用点**就是这个按钮（菜单里没有第二条路），所以面板已经开着分屏时再把它
拖到 ≤648px 就关不掉了，得把面板拖宽才回得来。取舍与 §6「中列视图名」那条同源：窄档牺牲一个功能键。

### R6 — 分栏语义反转：从「视图副本」到「冻结对象」（2026-09-13 用户要求）

**要解决的问题**：R4 的分栏是「当前视图的只读副本 + 按文件各自记忆」，于是右侧的内容永远等于
「左侧当前对象」的某个视图 —— 用户想在右边**钉住**一份东西、左边继续翻，做不到。

**用户原话（使用场景，即验收脚本）**：「点击 deepseekHARNESS，出现目录概览，点击分栏之后当前的
目录概览右侧冻结，再点击 packages 会出现 packages 的目录概览在左侧，这样就是我的目标」。

**目标**

| 项 | 行为 |
|---|---|
| 冻结的是谁 | **对象 + 视图类型一起冻**：点分栏那一刻的打开对象（`opened`）与它正在显示的视图（`viewer.mode`）一起记进 `SplitTarget` |
| 左侧切对象 | 右侧**不动**（不消失、不跟着换），一直显示那个被冻结的对象。文件与目录一视同仁 |
| 左侧切视图 | 右侧**不动**（视图类型同样冻结）。源码 ↔ 文件摘要 ↔ 源码注解 ↔ 文章翻译四类都不影响右侧 |
| 右侧数据 | **活的，不是死快照**。左右是**同一个对象**时（刚点完分栏那段）右侧沿用左侧那份 viewer ⇒ 左侧重新生成 / 保存后右侧跟着刷新；左侧一旦切到别的对象，两侧互不影响 |
| 分栏状态 | **全局一份**，不再按 path 各记各的。切对象保持开启、右侧保持那个冻结对象 |
| 拖拽比例 | **不再按对象记**（用户原话「拽比例 不用记得」）：就一个当前值，切对象、开关分栏都沿用；**不引入任何持久化**（不写 `UiState`、不碰 localStorage） |
| 只读 | 右侧仍恒只读（`editMode` 硬 false、`onTrDone` 传 null）—— R4 的这条不许破坏 |
| 界面 | **不新增任何 DOM 元素、不新增图标**：本单只改状态与数据来源，DOM 结构与基线逐档一致（见「验收」） |

**做法**（全在 client 侧 `src/client/index.tsx`；`src/host/**` 一字未动）

| 项 | 值 |
|---|---|
| 状态 | `const [splitTarget, setSplitTarget] = React.useState<SplitTarget \| null>(null)` + `const [splitRatio, setSplitRatio] = React.useState(SPLIT_RATIO_DEFAULT)`；`splitTarget === null` 即「关着」。R4 的 `splits: Record<path, SplitState>` 整个删除 |
| 数据源两支 | 左右 path 相同 ⇒ 复用左侧 viewer（天然 live）；不同 ⇒ 渲染一个新子组件 `SplitPane({frozen, grow})`，它内部 `useOpenedViewer(frozen.opened, null)` 起**自己的一份**实例（**A 类修正（2026-09-13，本条之后补记）**：独立支改为渲染开启那一刻从左侧 viewer 拷来的**数据快照**，不再重读 host —— 见下面的「A 类修正」补记） |
| 为什么用子组件 | hooks 规则禁止条件调用 hook，但**条件挂载子组件是允许的**：独立实例只在确实需要时挂载，不必为未开启态造占位对象（那会让 `useOpenedViewer` 的 `useEffect` 反复重读 host） |
| 同一性判据 | `opened.path`（`/tree` 下发的**项目根相对路径**，根为 `.`、书库文档形如 `.book/note.md`）。用 `name` 不行（不同目录可同名），`TreeNode` 也没有别的稳定 id 字段。**B-3 修正（本表之后补记）**：切工作区后 path 命名空间换掉，同名 path 会误判同对象 ⇒ 判据改为「`frozen.curWsId === curWsId` **且** path 相同」，`SplitTarget` 加 `curWsId` 字段 |
| key | 右侧窗格的 `key` 绑**冻结对象**的 path（不是左侧当前 path）：左侧每切一次对象，右侧都不该被卸载重建、重拉一遍数据 |
| 按钮 `disabled` | 由 `!opened` 改为 `!opened && !splitOn`：没有东西可冻**且**没有东西可关时才禁用（否则左侧被清空后就没有关闭分栏的入口了） |
| 拖拽守卫 | `startSplitDrag` 的守卫由左侧 path 改为 `splitTarget`：右侧开着就该能拖，与左侧此刻有没有对象无关 |

**判据（逐条都钉在 `tests/client-view.spec.ts` 的 `split view: the frozen target (R4 → R6)` 里）**

1. 冻结对象 + 视图类型 ⇒ `freezes the open object together with the view type`（并断言同对象支**不重复读**源文件）
2. 左侧切对象右侧不动 ⇒ `keeps the frozen object on the right while the left switches objects`（**A 类修正**：右侧渲染数据快照，不重读 host ⇒ 断言冻结对象**不被多读一次**，即读次数保持不变）
3. 左侧切视图右侧不动 ⇒ `freezes the view type: left-side view switches never touch the right pane`（正反各一次）
4. 同对象时右侧 live ⇒ `keeps the right pane live while both sides show the same object`（左侧重新生成文件摘要 ⇒ 右侧同一帧变）
5. 全局一份 ⇒ `keeps one global split: every object keeps the frozen right pane`（切文件、切目录都不关；关掉后切回原对象也**不**自动分栏）
6. 比例不按对象记 ⇒ `drags the divider, clamps the ratio and keeps one ratio for every object`
7. 恒只读 ⇒ 判据 1 / 3 两条里的 `button` 与 `.fs-area` 计数断言

**验收（几何）**：`--wsicon`（7 场景 × 551 档 = 3857 档）与基线 `out-final-lian3.json` **逐档逐字段 0 差异**
（跨列 0 档、同列 0 档、右列被整块裁下界 339、`hbarH {48}`）；分屏态 `--splitpane` 与
`out-final-lian3-split.json` 同样 **0 差异**。产物 `out-split-freeze.json` / `out-split-freeze-sp.json`。
逐档实测与边界清单见 `docs/agent/reports/2026-09-13-split-freeze-target.md`。

**已登记的边界**：左侧对象在分栏开启期间被清空、冻结对象被删 / 改名 / 换工作区 —— 清单与逐条
事实见该报告的「边界」一节（**不编造**：无法处理的如实登记为已知边界）。

**B-3 修正（本条目之后补记，历史时态）**：上文把「同一性判据」写成 `opened.path` 一项 —— 那是
R6 落地时的实现，随后被登记为已知边界 B-3：切工作区后 `path` 的命名空间整体换掉，两个不同工作区
可以各有一个同名 path，只比字符串会被误判成「同一个对象」而走复用支（右侧跟着跳到新工作区的同名
对象）。2026-09-13 已修：`SplitTarget` 加 `curWsId` 字段（开启那一刻的工作区 id），判据改为
**工作区相同且 path 相同**；右侧在切工作区后仍显示冻结那个工作区里的对象。

**A 类修正（本条目之后补记，历史时态，2026-09-13 用户裁决要修）**：上文把独立支写成「另起一份
`useOpenedViewer` 重读 host」—— R6 落地时的实现，随后被登记为已知边界 **A-1（邻居问题）** 与
**B-2**：独立支照 `frozen.opened.path` / `docRel` 去 `/read`，而 host 的 `/read` 按**当前 root**
解析相对路径 ⇒ 切工作区后新工作区存在同名路径时会读到**新工作区的内容**（A-1）；冻结对象在左侧
被删 / 改名后该次 `/read` 直接失败 ⇒ 右侧显示读取失败文本、无自动处置（B-2）。2026-09-13 已修：
`SplitPane` 不再调 `useOpenedViewer`，改为渲染**开启那一刻从左侧 viewer 拷来的数据快照**
（`SplitTarget.snap`，字段 = `FsPane` 查看分支渲染所需的全部数据字段，不含任何方法）——
不依赖当前 root（A-1 解）、不随对象删除消失（B-2 解），且**不再新增任何 host 调用**（反而消掉
