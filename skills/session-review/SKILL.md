# /session-review — 三个文档技能执行质量评判

对**文件系统插件内三个技能**的某次执行会话做复盘打分。不评通用能力，只评这三个技能各自的**产物验收点**是否达标。

**三个技能 & 产物层**：
| 技能 | 层级 | 产物目录 | 一句话目标 |
|---|---|---|---|
| `folder-doc` | L1 目录层 | `目录概览/` | 每个目录一份"这层有谁、各干什么" |
| `file-doc` | L2 文件层 | `文件摘要/` | 每个文件一份"这一页在干什么、为什么" |
| `source-doc` | L3 源码层 | `源码注解/` | 逐行中文注解，术语内联 |

**一句话原则**：产物与索引**以磁盘为准**，不信会话里模型的自述；每个扣分点必须落到具体证据（行号 / 索引条目 / 文件）。

## 第 0 步：定位与解析（用配套脚本）

```bash
node scripts/parse-session.mjs "<标题子串>"        # 反查会话 + 自动提炼关键事件
```

脚本输出：会话 id / 标题 / 日志路径；其次**自动过滤流式碎片**（reasoning-chunks/text-chunks/assistant-chunk/tool-call-chunks），只留 `user/message`、`assistant/message`、`tool/call`、`tool/result`、`turn/end`、`todo/write`、`session/title`；再统计工具调用序列、turn/step 数、每轮最终回复。

脚本返回 `--tag <skill>` 时可选：按技能名预筛是否需要读对应产物目录。**脚本不评分**，只负责把"模型做了什么"这件事摊开；**评判判断由你对照评分卡完成**。

## 第 1 步：判定执行的是哪个技能、哪个产物

看 user 初始消息与产物落点，判定 `folder-doc` / `file-doc` / `source-doc` 三选一，并确定对应书库根与产物。用 `find-session.mjs` 可知 cwd，产物通常在集中书库 `$DSH_HOME/books/<projectKey(项目根绝对路径)>/<产物层>/`（旧 `.book/<项目名>-book/` 为迁移前只读兼容位置）。

## 第 2 步：按技能专属评分卡打分

**每个技能一张卡，各 5 项**，每项 0-2 分（0 未做/做错，1 部分，2 达标），合计 10 分。评分时**同时核对产物文件与索引**，判定"是否达标"以磁盘为准。

### folder-doc（L1）
| 项 | 验收点 | 达标判据 |
|---|---|---|
| 范围 | 只处理目标目录树，排除 `.git/node_modules/.book` 等 | 目录概览里无排除目录；`--depth` 若指定则深度正确 |
| 命名 | `<项目名>.md` / `<文件夹名>.md` / 同名加父级前缀 | 文件名与实际目录一一对应，无遗漏无冗余 |
| 内容 | 每目录有"一句话说明"、子目录/文件表、目录树带 `--` 简介 | 描述具体（"协议库源码"）而非"一些代码文件"；不编造，不确定标"推测" |
| 目录树 | 用 `gen-tree.sh` 取真实骨架，子文件夹不展开 | 目录树与真实文件系统一致，非手写 |
| 索引 | 只写"目录层"数组，保留"文件层"不动；文档路径相对书库根 | index.json 目录层含该目录条目；文件层数量未变 |

### file-doc（L2）
| 项 | 验收点 | 达标判据 |
|---|---|---|
| 范围 | 只分析用户指定的文件，未指定则列包清单（排除测试/配置/锁文件） | 只生成了目标文件；未越界 |
| 核心概念 | **一段话**：所有导出合起来只干一件事，不允许并列 | 没有"A/B/C 三功能"式并列；是本质提炼 |
| 主线走查 | 按调用/依赖顺序，被依赖的先讲；每条有"做什么+为什么设计" | 有真实动机或明确"推测：……"；顺序合理 |
| 真实引用 | "被引用"用 grep 实际结果，不写"推测被引用" | 引用列表有 grep 依据；导出接口表来自真实代码 |
| 索引 | 只写"文件层"数组，保留"目录层"不动 | index.json 文件层含该文件条目；目录层数量未变 |

### source-doc（L3）
| 项 | 验收点 | 达标判据 |
|---|---|---|
| 范围 | 只注解用户指定文件，绝不批量 | 源码注解目录只新增目标文件这一篇 |
| 行号 | 注解行标注 `// [N]` 或 `// [起-止]`，与源码真实行号对齐 | 抽查若干行，行号↔源码一致（可用 `--src` 权威取码） |
| 排版 | 代码行>78 或 注解>30 字 → 行上方，否则行尾 | 长行被正确上浮；缩进与代码一致 |
| 术语 | 首次出现的英文术语/名称写 `English（中文）` 内联注译，只给真术语/名称加（中文） | 产物出现内联注译；变量名（ctx/i/m）不加括号；无独立"术语表"章节（"不生成集中术语表"这类正向说明属正常） |
| 索引 | 只写"源码层"数组，保留目录层/文件层不动 | index.json 源码层含该文件条目；目录层/文件层数量未变 |

## 第 3 步：输出评分表

```
评分：X/10（等级）

| 维度 | 得分 | 证据 | 评语 |
|---|---|---|---|
| 范围 | 2/2 | … | … |
……（5 项逐行）

扣分点（说明哪项为何没拿满）：
1. …
关键经验（可选，值得记入知识库的）：…
```

等级：9-10 优秀 / 8-9 良好 / 7-8 合格 / <7 需改进。

## 注意

- **产物与索引以磁盘为准**，模型自述只当线索，不当证据。务必 `ls` 产物目录、`cat` index.json、抽查产物行。
- 流式碎片已由脚本过滤，你勿再手动 grep 日志找标题（标题在投影缓存）。
- "术语表"字样：在 source-doc 产物里可能是**正向说明**（"不生成集中术语表"），判断新旧约定看上下文，别误判为回退。
- 被注解源码若是"生成 Markdown 的元代码"，产物里的 `\`\`\`` 是源码转义、非缺陷（source-doc 自举会话踩过）。
- 只评分，不修改会话/产物/索引；记录经验可写入插件 `issues/` 知识库。
