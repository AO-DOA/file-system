# /source-doc — 源码逐行中文注解

> **版本**：1.0

在每行代码前插 `// [行号]` 中文注解，原注释翻译后并入注解行、原注释删除，形成源码一样流畅逐行可读的中文版。首次出现的名词/方法名就地写 `English（中文）` 给中文翻译（内联注译）。产出集中存入 `<书库根>/源码注解/`，并维护 `index.json` 的「源码层」。

**一句话**：模型只写语义（含英文术语/名称的内联注译），其余（行号/排版/索引/校验）全由脚本 `scripts/source-annotate.mjs` 保证。

## 第零步：定位（先查事实，再列清单）

1. **书库根**：`--book <书库根>`（集中模型 `$DSH_HOME/books/<projectKey(项目根绝对路径)>/`，桶名算法与 DSH format.ts 一致，无 `<项目名>-book` 中间层；宿主给的值优先，**传了就用它**；未传则脚本自动推导新桶，build 推荐传 `--root <项目根绝对路径>` 或依赖 `--src`/`--rel` 推导）。可先 `node scripts/source-annotate.mjs layout <项目根>`（只打印布局，不覆盖）确认目录结构。
2. **源码路径键**：`工作区名 + '/' + 相对工作区根的路径`（目标即工作区根时为工作区名本身）。这是 `--rel` 的值，也是 frontmatter「源码路径」与 index.json「源码层」的键。
3. 产物命名由脚本自动算（完整相对路径前缀，与 file-doc/folder-doc 一致），模型不手算；同名歧义时用 `--doc-name`。
4. **单文件不批量**：一次只对这一个源码文件生成一篇——这是宿主触发的唯一目标，绝不批量为其它文件生成多篇。
5. **检查 → 再列清单 → 后执行**。先探查（读源码、确认 index.json），再用 `todo_write` 编排，执行中与真实不符就改计划。

## 第一步：范围

1. **目标是宿主点选的这一个源码文件**，只分析它自身，绝不批量。
2. 排除二进制、图片、锁文件、>1MB、node_modules、`*.spec.*`、`tests/`（用户点名才做）——这些都是"目标本身就是这类文件"时才跳过，不影响正常源码文件。
3. 逐行注解体量大，**一个文件内部**按块分批：每批 ≤300 个可注解单元（skeleton 输出会计数），大文件分多次走「骨架→填→build」。

## 第二步：读文件

1. 通读全文，标出所有方法/函数/导出常量。
2. 读文件时**识别**首次出现的名词/方法名/类型名/缩写，每个都想清其中文翻译，为第三步内联注译备料（写成 `English（中文）`，**只内联不汇总**）。
3. 理解每方法：做什么（一句）、为何这么设计（JSDoc 动机）、输入输出。

## 第三步：生成（三个命令）

脚本：`node scripts/source-annotate.mjs <layout|skeleton|build> ...`（相对技能根，仅用 Node 内置模块）。模板/排版/行号/索引由脚本保证，**模型不手写**。

> **分批**：一个文件内的全部过程（骨架→填注解→build）是**一次动作**，别在文件内部混着并行填；体量大就按单元数分批，每批走完整三步。

1. **骨架**：`node scripts/source-annotate.mjs skeleton <源文件> --skeleton <临时骨架>`。脚本按真实行号切可注解单元（连续注释合并为块 `[起-止]`、代码行逐行、纯符号/空行跳过），输出填空题。顶部有 `@摘要` 字段（填一句"这页代码解决什么问题"，build 写入「> 解决什么问题」；不填则保留占位）。
2. **填注解**（模型主干）：通读源码后，在骨架每个 `注解:` 后写该行/该块的中文释义。只填语义，不改行号与代码行。**严格逐单元填，一条单元只写它自己的释义**——块头行与其内部形参是不同的独立单元，不得合并单元边界（否则丢行号，见 issue [06]）。首次出现的英文术语/名称统一写 `English（中文）` 就地给中文。
3. **成品**：`node scripts/source-annotate.mjs build <骨架> --rel <源码路径键> --book <书库根> [--root <项目根绝对路径>] [--src <真实源路径>] [--doc-name] [--no-index]`（未传 `--book` 时脚本自动 = `$DSH_HOME/books/<projectKey(项目根)>/`）。`--rel` = **工作区名 + `/` + 文件相对工作区根的路径**（与 file-doc/folder-doc 同规则，如 `DSHworkPace/plugins/.../src/index.js`），写入 frontmatter（源码路径/层级: 源码/生成时间，生成时间=本次生成时刻，重生成即刷新）与 index.json。文档命名由脚本自动算（完整相对路径前缀，与 file-doc 一致），不传 `--pkg`。脚本自动完成：
   - 按源码真实行号取码，标 `// [N]`（单行）或 `// [起-止]`（块/跨行）；
   - 排版：代码行 >78 或 注解 >30 字 → 行上方，否则行尾；
   - 块的原注释删除（释义已并入），行内注释保留；
   - 术语/名称的 `English（中文）` 翻译原样保留在注解里（内联注译，不汇总）；语言标签按扩展名推断；
   - 写入 `<书库根>/源码注解/<脚本自动命名>.md`（完整相对路径前缀），并更新 index.json「源码层」；
   - 自检排版/行号，最后删骨架。
   - `--src` 仅在跨项目需权威行号时传，否则默认用骨架内代码。

**注译写法**：首次出现的英文术语/名称，就地写 `English（中文）`（英文后跟一对中文圆括号给翻译），读者顺读即懂。只给真正的领域/专有术语/名称加（中文）（如 `Run`、`esbuild`、`createRequire`），**不要**给变量名/局部变量（`ctx`、`i`、`m`）或普通英文词/JS 关键字加（中文）。翻译只内联在注解行里，不另建汇总。

## 第四步：索引与汇报

1. 索引由 build 自动追加「源码层」，无需手写。
2. 分批：一个文件内部按单元数分批（每批 ≤300 单元），每批走完「骨架→填→build」即落盘。
3. 汇报：生成清单（文档↔源码路径）、跳过的文件及原因、推测性内容。

## 第五步：问题记录（自检）

先做实质判断——**这轮是否顺利，有没有值得沉淀给技能的坑**（不顺利就见招拆招后记下）。常见如脚本报错、参数不生效、返工、产出不符预期、路径失效、判断失误等，但**不限于此**——只要是这轮暴露出的、下次可能再踩的，就按 `plugins/dsh-plugin-file-system-zc/issues/_template.md` 记一条到 `issues/<date>-<序号>-<slug>.md` 并更新 `issues/README.md` 索引表。**顺利则跳过，保持零噪声**。

## 注意

- 同名文档直接覆盖；全简体中文，代码/路径/专有名词保留原文；目标内含 `.book` 则跳过。
- 脚本随本技能目录分发（`scripts/source-annotate.mjs`），可随包迁移。
- 模型不要在注解里写 `// [N]` 这类数字——行号由脚本按真实行号保证，写了也不生效。
- 与 file-doc 分工：file-doc 讲"这个文件干什么"（宏观），source-doc 讲"每一行在干什么"（微观）；同名命名分放 `文件摘要/` 与 `源码注解/`，不冲突。
