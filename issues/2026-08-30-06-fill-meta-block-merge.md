# 填充时把独立源码行的注解挤进前一行，导致行号错位（meta = { ... } 大块）

> 使用 `source-doc` 为 `opencode.nix` 生成源码注解时，发现旧产出里 `meta = { ... }`（第 102-109 行）的逐行注解被错误地压缩成一行 `// [102]`，`description/homepage/license/mainProgram/platforms` 的真实行号 103-107 全部丢失。

## 场景（怎么触发）

对多行成块结构（如 `meta = { ... }`、`passthru = { ... }`、长函数参数列表）填充骨架时，模型没按骨架每个 `@行 [N]` 单元逐个填注解，而是把语义较顺的一组行合并写进了第一个 `@行` 的 `注解:` 后。

命令：`node scripts/source-annotate.mjs skeleton <源文件> --skeleton <骨架>` → 在骨架逐个填 `注解:` → `build`。

## 现象（看到了什么）

- 骨架里 `@行 [102]`（`meta = {`）到 `@行 [107]`（platforms）、`@行 [109]`（`})`）是**各自独立的空单元**，但旧产出把 103-107 的解释挤进了 `// [102]` 一行。
- 产物里缺失 `// [103]`~`// [107]` 这些独立注解，`meta = {` 被当成"整块的开始+首行"合并展示。

## 根因（为什么会这样）

**不是脚本 bug**：脚本骨架切分、行号、build 的排版/术语/索引都正确（本次用修正后脚本重跑，骨架 `@行 [102]~[107]` 分别独立）。
根因在**模型填充的流程约定**——模型连续阅读代码块后，倾向把"语义连贯的一整块"写成一句注解，而非严格按骨架的**每条 `@行` 填独立语义**。这在"块头行（`meta = {`）只算一个单元、其后属性是另一批单元"的结构里特别容易踩。

配合 [02] 的教训，进一步说明：**骨架给的单元边界 + 行号是权威，模型务必"一行一条"地填**，不要凭语义连贯性合并。

## 改法 / 临时绕过

临时：本次重跑骨架，按每个 `@行` 的 `代码:` 原文（strip 后）逐条精确填充，`meta = {` 与 103-107 各自单独填，build 后行号正确。

改法建议（技能侧）：在 SKILL.md 第三步"填注解"加一条硬约束——**按骨架每个 `@行`/`@块` 单元逐一填，块头行（如 `meta = {`、`function (…{`）与其内部属性是不同单元，不得合并成一句**；可顺带在"疑似术语候选"提示里强调"每单元一行，不跨行合并"。

## 复验（如何确认已解决）

对结构含多行成块的文件（如 `meta = {`、`passthru = {`）重新 build，grep 产物 `// \[10[2-9]\]`，能看到 `[102][103][104][105][106][107]` 各自独立占一个注解行、无合并。
